# NSWRC 管理システム セキュリティ運用手順

最終更新: 2026-11-16

この文書は、全国学生無線通信研究会の会員管理API・管理画面・Supabase Databaseを運用するための手順です。設定が未確認の項目は「未確認」と明記しています。これだけで法令・規格への適合を保証するものではありません。

## 1. 実装済みの保護策

- 管理APIはSupabase Authでユーザーを検証し、app_metadata.role が admin であることを確認します。
- 管理APIはMFA済みセッション（JWTのaal2）を必須とします。初回アクセス時、管理画面でTOTP認証アプリの登録・認証を案内します。
- 免許証番号の表示・登録・変更と暗号化鍵ローテーションは、直近5分以内のTOTP認証を追加で要求します。
- 管理セッションは認証時刻から最大12時間でAPI側が拒否します。ログアウト時はセッションIDを失効テーブルへ登録し、以後の管理APIアクセスを拒否します。
- 一般の会員・申込一覧APIから免許証番号を除外し、専用APIから追加認証後にのみ返します。
- 免許証番号の閲覧、一覧閲覧、変更操作、CSV出力、ログアウト、鍵ローテーションをadmin_security_auditへ記録します。
- 管理API・公開申込・お問い合わせにDBベースのレート制限を適用します。
- anon / authenticated の公開テーブル権限を取り消し、RLSの制限ポリシーを追加しました。ブラウザーからのDB直接アクセスは想定せず、サーバーAPIがService Roleで処理します。
- PII暗号化はAES-256-GCMを使用し、旧形式enc:v1を復号しながら、鍵IDを持つenc:v2へ段階移行できるようにしました。
- 新規お問い合わせでは氏名・メールアドレス・所属・本文を暗号化して保存します。管理画面APIでのみ復号し、運営メモも暗号化して保存します。既存の平文レコードは復号関数がそのまま返すため、段階移行できます。

## 2. 管理者アカウント

1. 管理者ごとに個別のSupabase Authアカウントを使用してください。共有アカウントは使用しないでください。
2. 管理者のapp_metadata.roleにadminを設定してください。user_metadataを権限判定に使用しないでください。
3. 管理画面へログインすると、TOTP認証アプリの登録・確認を求められます。QRコードを認証アプリで読み取り、6桁コードを入力してください。
4. 認証アプリの機種変更・紛失に備え、Supabase AuthのMFA回復手段を安全な場所に保管してください。
5. 退任・紛失端末・不審なアクセスがあった場合は、該当アカウントのセッションを失効させ、必要に応じてパスワード変更・MFA再登録を行ってください。

### セッションの仕様

- Supabase JS Auth SDKのセッション永続化を使用します。現在のGitHub PagesとVercelの別オリジン構成では、HttpOnly Cookieによる同一オリジンセッションではありません。
- 管理APIは認証時刻から12時間を超えたセッションを拒否します。
- ログアウトAPIでセッションIDをサーバー側失効リストへ登録します。
- ブラウザーのストレージを消去した場合やセッションが失効した場合は再ログインが必要です。

## 3. 免許証番号などの機微情報

- 一般の /api/admin-members と /api/admin-applications の一覧応答には免許証番号を含めません。
- 管理画面の「番号を表示」からTOTP認証を行うと、/api/admin-sensitive が対象レコードの免許証番号を返します。
- 閲覧操作は、管理者ID・メールアドレス・対象レコードID・時刻とともに監査ログへ記録されます。免許証番号そのものはログへ保存しません。
- 免許証番号の新規登録・変更も、直近5分以内のTOTP認証が必要です。
- CSVには免許証番号を含めません。CSV出力操作は監査ログへ記録されます。

## 4. お問い合わせ情報の保護\n\n- 公開お問い合わせAPIは氏名・メールアドレス・所属・本文を保存前にAES-256-GCMで暗号化します。\n- 管理画面の問い合わせAPIは、認証済み管理者に限って表示時に復号します。\n- 管理者が記録する運営メモも暗号化して保存します。\n- 既存の平文データは復号処理で読み取れますが、過去レコードの再暗号化は別途移行作業が必要です。\n- 暗号化鍵が利用できない場合、新規受付・メモ保存は失敗させ、平文保存へフォールバックしません。\n\n## 5. 暗号化鍵の保管とローテーション

### 保管原則

暗号化鍵はVercelのサーバー環境変数だけに保存してください。GitHub、HTML、JavaScript、Issue、チャット、ログ、バックアップとは別に管理してください。鍵を紛失すると暗号化済み個人情報を復号できません。

### 環境変数

既存データの復号に必要な旧鍵を保持したまま、新しい鍵を追加します。

- NSWRC_PII_ENCRYPTION_KEYS: JSON形式の鍵IDと64桁hex鍵の対応表（enc:v2用）
- NSWRC_PII_ACTIVE_KEY_ID: 新規暗号化に使用する鍵ID
- NSWRC_PII_ENCRYPTION_KEYまたはPII_ENCRYPTION_KEY: 旧enc:v1データを復号するための移行用旧鍵（移行後も検証が終わるまでは削除しない）。旧鍵は鍵リングへ複製せず、この環境変数に残しても復号できます。

例（値は説明用のプレースホルダーであり、実際の鍵ではありません）:

~~~json
{"nswrc-2026-11":"<新32-byte hex鍵>"}
~~~

新しい鍵は安全な端末で暗号学的乱数から生成し、VercelのProduction環境変数へ登録してください。鍵の実値をこの文書やリポジトリに記載してはいけません。

### ローテーション手順

1. 現行の旧鍵を安全な保管場所で確認し、復号可能な状態を維持します。
2. 新しい32-byte鍵を生成します。
3. NSWRC_PII_ENCRYPTION_KEYSへ新しい鍵IDと新鍵を登録します。旧enc:v1用の鍵は、既存のNSWRC_PII_ENCRYPTION_KEY / PII_ENCRYPTION_KEYに残します。
4. NSWRC_PII_ACTIVE_KEY_IDを新しい鍵ID（現在設定済み: nswrc-2026-11）に設定し、Vercelへ再デプロイします。
5. 管理画面の「環境設定」→「暗号化鍵のローテーションを実行」を開き、追加認証を行って実行します。
6. 会員・申込の両テーブルで処理が完了したことを確認します。
7. 別途、DB内に旧鍵IDのenc:v2データやenc:v1データが残っていないことを確認します。
8. 新鍵で代表レコードの復号・画面表示・編集ができることを確認します。
9. バックアップにも旧鍵が必要なことを確認したうえで、旧鍵を削除する判断を行います。旧鍵を削除すると、その鍵で暗号化されたバックアップを復号できなくなります。

**重要:** 旧鍵を削除するのは、全レコードの再暗号化とバックアップ復元テストが完了してからです。鍵ローテーション中は旧鍵・新鍵の両方を保持してください。

## 5. レート制限

現在の初期値:

| 対象 | 上限 |
| --- | ---: |
| 管理会員API | 120回 / 管理者 / 1分 |
| 管理申込API | 120回 / 管理者 / 1分 |
| 監査ログAPI | 60回 / 管理者 / 1分 |
| 免許証番号閲覧 | 5回 / 管理者 / 5分 |
| ログアウトAPI | 10回 / 管理者 / 10分 |
| 暗号化鍵ローテーション | 20回 / 管理者 / 5分 |
| 公開入会申込 | 3回 / IP / 1時間 |
| 公開お問い合わせ | 5回 / IP / 1時間 |

DB関数による固定ウィンドウ方式です。運用状況に応じて閾値を調整してください。CDNやプロキシのIPヘッダー仕様が変わった場合は、IP単位の制限が正しく機能するか確認してください。

## 6. データベース権限とRLS

以下のマイグレーションを適用済みです。

- admin_security_hardening
- admin_session_revocation
- deny_direct_public_table_access

anon / authenticated には公開スキーマの利用権限・対象テーブル権限を与えず、RLSにも拒否ポリシーを設定しています。アプリケーションのデータ操作はVercel API経由に限定します。SUPABASE_SECRET_KEY / SUPABASE_SERVICE_ROLE_KEYをブラウザーへ出してはいけません。

## 7. バックアップと復元

### 現在の契約プラン

2026-11-16時点で接続情報から確認したプラン:

- Supabase: **Free ($0/月)**
- Vercel: **Hobby ($0/月)**
- Supabaseプロジェクト: ACTIVE_HEALTHY

Supabase Freeには自動バックアップがありません。Proは日次7日、Teamは日次14日、Enterpriseは最大30日保存です。PITRは有料アドオンです。詳細は[Supabase Database Backups](https://supabase.com/docs/guides/platform/backups)を参照してください。

### 無料枠を使った代替バックアップ

GitHub Actionsで毎週日曜日12:00（日本時間）に、Supabaseのpublicスキーマとデータをダンプし、AES-256で暗号化したアーカイブを7日間保存するワークフローを追加しました。

ファイル: `.github/workflows/weekly-db-backup.yml`

**有効化に必要な設定（GitHub側）**

リポジトリの Settings → Secrets and variables → Actions → New repository secret から、次の2つを登録してください。

1. `SUPABASE_DB_URL`: Supabase DashboardのDatabase接続文字列。可能ならSession poolerの接続URIを使用してください。DBパスワードを含むため、公開Issueやコードに書かないでください。
2. `BACKUP_ENCRYPTION_PASSPHRASE`: 十分に長いランダムなバックアップ専用パスフレーズ。暗号化鍵とは別の安全な場所にも保管してください。

登録後、Actions → Weekly encrypted NSWRC database backup → Run workflow で初回実行し、成功と暗号化Artifactの作成を確認してください。Secretsはこの環境から登録できないため、上記2つが登録されるまではワークフローは実行に失敗します。ワークフローの追加だけでバックアップが開始済みになったわけではありません。

GitHub Freeの標準Actionsには月2,000分・Artifact等の共有ストレージ500MBが含まれます。週1回・7日保存の運用はこの枠内を想定していますが、他のActions/Packages使用量とバックアップサイズ次第で上限に達する可能性があります。無料枠を超えた場合に課金が発生しないよう、GitHubのActions予算・利用上限も確認してください。詳細は[GitHub Actionsの無料枠](https://docs.github.com/ja/billing/concepts/product-billing/github-actions)を参照してください。

**バックアップの対象外・制約**

- このワークフローはSupabaseのpublicスキーマの構造とデータを対象にします。
- Supabase CLIの標準ダンプはSupabase管理のauth / storageスキーマやStorage内ファイル本体を含みません。管理者Authユーザー、認証要素、Storageファイルは別途復旧手順が必要です。
- Artifactは7日で自動削除されるため、長期保存や30日保存の代替ではありません。
- 公開リポジトリのActions Artifactはリポジトリ閲覧者が取得できる可能性があるため、暗号化済みファイルのみアップロードします。パスフレーズはリポジトリに保存しないでください。
- バックアップの取得成功だけでは復元可能性を保証しません。別環境での復元テストが必要です。

### 復元の基本方針

1. GitHub ActionsのArtifactから暗号化ファイルを取得します。
2. 安全な端末で専用パスフレーズを使って復号します。
3. アーカイブ内のschema.sqlとdata.sqlを確認し、まず別のSupabaseプロジェクトへ復元します。
4. RLS・GRANT・ポリシー・トリガー・関数・暗号化鍵設定を確認し、会員件数・申込件数・代表レコード・暗号化データの復号を検証します。
5. AuthユーザーとStorageファイルは、別途再作成・復元が必要です。
6. 本番へ直接復元する前に、実施者・日時・復元ポイント・影響範囲を記録してください。

### 推奨運用

- バックアップArtifactは7日保存の短期復旧用とし、重要な変更や鍵ローテーション前には手動バックアップも取得します。
- 保存先の追加や長期保存を行う場合も、暗号化した状態でアクセス権を限定します。
- 少なくとも四半期に一度、別プロジェクトまたは隔離環境へ復元し、会員件数・申込件数・代表データ・暗号化データの復号を確認します。
- Storageを使用する場合、DBバックアップだけではファイル本体を復元できない点に注意してください。

## 8. 残っている運用確認

- Supabase Freeでは「Leaked Password Protection」は提供対象外です。Pro以上の機能なので有効化しません。無料運用では管理者に12文字以上の固有パスワードとTOTP MFAを必須にし、漏えいの疑いがあれば即時変更・セッション失効する運用で補います。漏えい済みパスワードとの自動照合は行いません。
- Supabase FreeのためSupabase標準の自動バックアップはありません。GitHub Actionsの暗号化バックアップはワークフロー追加済みですが、GitHub Secrets 2件の登録と初回成功確認が未完了です。
- GitHub Actions Artifactは7日保存の短期バックアップです。長期保存・Authユーザー・Storageファイルの復元は別途設計が必要です。
- バックアップの復元テストは未実施です。
- 監査ログの保存期間は未決定です。保存期間・閲覧権限・削除手順を運営規程として決めてください。
- 実ブラウザーでのログイン・TOTP登録・再認証・ログアウト・CSV出力のE2Eテストは未実施です。
